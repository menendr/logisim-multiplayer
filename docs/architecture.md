# Architecture

## Investigated 2.7.1 integration points

`Project.doAction` executes `Action.doIt`, maintains a single-user undo stack and fires ACTION_START / ACTION_COMPLETE / ACTION_MERGE events. Some tools combine several changes in an action; selection actions can contain floating clipboard components that are not yet part of a circuit. Project events occur on the Swing EDT. `CircuitAction` wraps a `CircuitMutation`; the latter accumulates additions, removals, replacements and attribute changes. `CircuitTransaction.execute` locks affected circuits and maintains wire repair and subcircuit dependencies. Its reverse transaction enables original single-user undo, but it does not provide distributed undo semantics.

`SelectionActions` implements duplicate, paste, drop, delete and translate through CircuitMutation. Paste can remain floating until a drop/translation action commits it to the model. Synchronizing selections would therefore confuse local UI state with committed circuit state. `Circuit` owns components, wires, static attributes and default/custom appearance. `LogisimFile` owns circuit membership, libraries, main circuit, options and serialization. `ProjectIO` is a package bridge to the original package-private writer. We do not replace the simulator or emulate input events.

## Feasibility gate

Before any collaboration hook was installed, the upstream build launched on Windows. FeasibilityProof captured an original AND-gate action through ProjectListener, replayed it using an independent factory and CircuitMutation, compared serialized project bytes and checked the original inverse transaction. This passed against the original JAR. A byte-order mark is stripped only in compile staging. Two legacy Swing TreeNode declarations require raw Enumeration return signatures when compiling against Java 17; those compatibility changes are documented and their original files retained.

## Editing protocol

The production hook intercepts allowed Project actions before execution. It calls the original action path on the EDT, then compares deterministic model descriptors before and after the logical action. Each transaction contains only changed circuit metadata, component descriptors or wires. It never sends a complete project for normal editing. Capturing attribute values uses Attribute.toStandardString; replay resolves original built-in ComponentFactory instances and Attribute.parse, then uses CircuitMutation. Options, selections, tool defaults, mouse positions, viewports and simulation state are excluded.

The client permits one pending transaction, showing Synchronizing until an acknowledgement arrives; another client can submit concurrently. Server-side per-target before-values plus last-touched revisions detect conflicts, including delete/recreate ABA cases. An old base revision is allowed only when every affected target has remained unchanged since that revision. Different targets can therefore commit without rebasing the entire project. The entire candidate circuit graph is checked for missing or recursive subcircuits.

The server is one synchronized Java authority. It materializes candidates using the original APIs and round-trips its own serializer output through the vanilla loader before persistence. Arbitrary client .circ XML is never loaded on the server. A failed precondition/validation/durable write does not change the authoritative record. The global revision increments only on commit. Operation receipts persist the client UUID, operation UUID and request hash. Retries return the original acceptance and cannot apply twice; reuse with different content is rejected.

Local changes are provisional. On a remote commit the client updates its accepted model and reconciles its live circuit; its own pending proposal remains in flight. Its acceptance is then replayed in server order, or a rejection restores accepted state. A lost connection removes provisional local structure from the view, freezes structural editing and retains the proposal in memory for idempotent retry. A client crash loses unsubmitted/unaccepted proposals, not accepted work. Revision gaps, duplicate/out-of-order commits and hash mismatches trigger authoritative snapshot recovery. Unchanged objects retain identity; changed attributes use replacement maps so local selections can follow replacements. Structural remote replay does not call Project.doAction and cannot echo outgoing operations.

## Threading, undo and simulation

Network callbacks enqueue all desktop updates through SwingUtilities.invokeLater. UI capture, original actions, reconciliation and application of remote mutations occur on the EDT. Server models have no Project, Frame or simulator. Normal Logisim transaction locks still protect simulation access. Both clients run local simulation; pokes/ticks are not shared. Replaced components and initial/recovery snapshots may reset simulation state.

Collaborative undo/redo are implemented as server-authorized inverse/forward transactions against per-client persistent history. Partner touches permanently invalidate affected entries, including ABA restoration; model/dependency validation still applies. Unrelated partner edits remain. Own successive inverses can traverse the same target safely. History is capped at 100 entries / 4 MB globally. The original single-user undo stack is bypassed during collaboration and cleared after reconciliation and when leaving. The Edit menu exposes Ctrl+Z, Ctrl+Y and Ctrl+Shift+Z with availability from authoritative history flags. Unsupported action classes are denied before execution. Candidate validation failures use the original inverse and then authoritative recovery; failures are displayed, never represented as committed changes. Uninstrumented model discrepancies are discarded and reported before the next local edit.

## Durability and resource limits

Each accepted revision produces an immutable generation containing project.circ and commit.json (state, revision, hash, receipts and per-target revision stamps). Files are fully written and fsynced, the staging directory is atomically renamed, and the parent directory is fsynced on Linux before acceptance. Windows does not expose directory fsync through the same Java API; process-restart recovery was tested there, power-loss guarantees were not. A single process lock prevents competing authorities on the same directory.

The server retains 32 recent generations and every 100th generation. On startup it verifies metadata/model hashes and .circ checksums and can fall back to a previous verified generation. A damaged newer generation forces recovered sessions read-only so unknown accepted changes are not silently overwritten. Failed and interrupted files are retained for review. The server exposes one shared project without invite tokens. A fixed storage key identifies a new project; migration can select a retained legacy directory using SHARED_PROJECT_KEY. Socket identity governs each client’s history, but network reachability now grants editing access. Multiple legacy directories are retained without exposing separate rooms; ambiguous migration requires an explicit selection.

All sessions share a serialized validation/write path, intentionally favoring simplicity for two trusted students over throughput. The protocol bounds sessions, peers, project size, message/frame size, nesting, transaction size, history and output queue length. Receipts are bounded rather than silently expired; start a new session after reaching the explicit transaction limit. TLS terminates at an existing reverse proxy; desktop wss uses ordinary JVM certificate verification.

## Saved connections and personal history across application restarts

SavedServers uses Java Preferences under the desktop user's local account, outside the executable JAR. It remembers up to eight server/name profiles and the most recently used profile. Existing address/nickname settings are migrated. Addresses are normalized/deduplicated; each server/name pair has a stable locally generated UUID. No session secret/password is stored, and no account system is added. A quick Connect item and Saved Servers submenu invoke the same connection path as the dialog. No automatic connection occurs at application startup. Removing a saved profile affects only local preferences, not the server project.

The stable profile UUID is sent as the clientId, so the existing server-authorized per-client history can be recovered after closing/reopening the desktop. Different names on one computer receive different identities; separate operating-system accounts/computers have independent settings. The same profile cannot be concurrently connected twice. Retention, partner-touch invalidation and full inverse validation still apply; this update does not turn undo into global project rollback. Older random per-launch IDs cannot be retroactively associated with newly saved profiles.
